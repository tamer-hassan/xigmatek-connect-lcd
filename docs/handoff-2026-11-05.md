## The two things this session settled

**1. Why the clock only moves every 20–40 s — and why it can't be fixed by sending
faster.** The panel composites an OSD layer (the newest uploaded `.osd` PNG) over a
static logo/theme image, and refreshes that OSD layer on its own timer. Measured with
eyes on a healthy unit:

| uploaded at 1 Hz, one second apart | seen on screen in 30–45 s | ended on newest? |
|---|---|---|
| flat solid colour, 1 584 B | 8–15 changes (2–3 s each) | yes (magenta) |
| big counter, 16–30 KB RGBA | 6 of 30 (~7 s) | no, ended on 24 |
| same counter, 6.4 KB indexed | 3 of 30 (~15 s) | ended on 28 |
| same counter, one frame per 5 s | 3 of 12 | yes, ended on 12 |
| overlay counter (89.9 % transparent), 14.9 KB | 7 of 30 (~6 s) | logo visible behind digits |

Byte-exact replay of ALPHA's *own* frames at the same cadence is equally slow, so the
encoder is not at fault and the vendor has the same visible rate. The panel always
jumps to the newest file it holds, never plays through its backlog, and latches the
last frame indefinitely. Cost tracks content, not bytes (flat 2–3 s, glyphs 6–15 s,
indexed no better than RGBA). **Conclusion: keep 1 Hz; a clock painted into a PNG
cannot tick smoothly on Linux or Windows.**

**2. There is no panel-drawn mode to switch to.** `realtimeDisplay {"enable":true}`
plus 25 s of `STATE all 1` metrics and zero uploads: only the static logo, no numbers,
nothing changed in `conn` — the topic acts as a display-layer toggle. The nine
"built-in themes" `presetThemeId {"index":0..8}` are accepted and visibly do nothing,
while being the writes that damage a unit. The `osd.widget[]` sources in ALPHA's
`store.json` are a red herring on this firmware.

## Danger, measured twice, now enforced in code

`POST logo`, `POST mode`, `POST presetThemeId`: **23 body shapes each**, every one
answers `200` and leaves that field at `2147483647`, the panel's "not set" — writing
`{"index":3}` to a panel reporting `logo=3` clears it. The running display is
unaffected, so the unit looks fine; the next cold POST is white from the first second,
and the panel's theme media is freed (`space` +1.3 MB). Power cycles do not undo it.

`Link` now raises `PermissionError` for `logo`, `mode`, `presetThemeId`, `theme`,
`themeBackground`, `logoSet`, `config`, `recovery`, `firmware`, `update`, `upgrade`,
`ota` and any `waterBlockScreen*` unless built with `allow_destructive=True`.
`tools/vendor_cmds.py` had `presetThemeId {"index":0}` in its SAFE list — that entry is
what blanked the unit the first time — and it is gone, along with that tool's
`--risky recovery` flag and the guessed `config {}` probe.

## The cure, from the vendor's own log

`2026-11-5.log` 18:39:48, the moment "AIO Theme → reset" was clicked in Windows:

```
POST recovery 1     {"enable":true}    109-byte frame -> 1 200 in 6 ms
+9 s: logo 2147483647 -> 3, mode 2147483647 -> 0, osdState 1 -> 0, space 69252 -> 69664
```

Our encoder reproduces that frame **109/109 bytes identical**. `tools/reset_panel.py`
sends it — dry run unless `--yes`, prints the frame first, waits for the device to
re-appear, re-reads state. Run here at 21:23: took
`logo/mode = 2147483647, space 68912` to `logo=3 mode=0 space=69664`, device back
after ~9 s, same free-space value the vendor's reset landed on.
